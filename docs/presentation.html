LogSentry · Nirav Mehta08
Owned by teams · no-code tuning

Change sensitivity without shipping code.

# config/thresholds.yaml
defaults:
  error_rate: { max_error_pct: 5.0, min_volume: 50 }
  fatal: { max_fatal: 1 }
  latency: { p99_ms_threshold: 2000 }

services:
  payment-service: # stricter for money paths
    error_rate: { max_error_pct: 1.0 }
    fatal: { max_fatal: 0 }
  batch-report-service: # quiet by design
    silence: { window_minutes: 360 }
  • Global defaults, with field-level per-service overrides.
  • Stricter rules for critical paths; looser for batch jobs.
  • Validated on load — a typo fails fast with a clear error.
  • Edit, redeploy, done. No engineer required.
LogSentry · Nirav Mehta09
Customer safety first

It cannot hurt production. By construction.

  • Read-only everywhere. No tool, query, or script can write to any production system.
  • Least-privilege identity. The runtime account holds only three viewer roles — no editor, no owner.
  • Query caps. Hard limits on rows and time windows bound both cost and blast radius.
  • SQL guard. Any mutating keyword is rejected before a query runs.

Runtime permissions — the entire list

roles/logging.viewer roles/bigquery.dataViewer roles/bigquery.jobUser

That's it. The agent literally cannot change production.

LogSentry · Nirav Mehta10
Built to lower the bill

The biggest cost lever, pulled by default.

  • Log tiering. Only severity ≥ WARNING is exported to BigQuery; high-volume INFO/DEBUG stay in the cheaper default bucket.
  • Query caps bound every scan — no runaway BigQuery bills.
  • Scale-to-zero. Cloud Run costs nothing when idle between cycles.
  • Alert dedup stops alert storms that burn API calls and attention.

Where the savings come from

~80%of log volume is INFO/DEBUG — kept out of the expensive path*

*Typical fleet ratio; actuals depend on app verbosity. Sampling at the log4j appender can cut it further.
